# HAMBOX architecture

_Last refreshed: 2026-10-16. Describes the system as deployed, not an aspirational design._

## Shape

A **modular monolith**: one ASP.NET Core (.NET 10) process, one SQL Server database, one Angular 21 single-page
storefront + back office served as static files by nginx. Modules own their tables (one schema each) and talk to
each other through interfaces in `HAMBOX.Application` (never through another module's `DbContext`).

| Module | Owns |
|---|---|
| Identity | users, roles/permissions, sessions, admin TOTP, platform settings, e-mail delivery |
| Catalog | products, variants, categories, inventory codes (encrypted), batches |
| Commerce | cart, orders, payments + gateway verification, holds, refunds, memberships, referrals, reviews, promotions, reports, the job engine |
| Suppliers | supplier accounts, provider clients (Bamboo, Visoria, GlobeTopper, Eneba, CodesWholesale), API call log |
| Communication | templates, per-channel delivery (e-mail, in-app, WhatsApp), preferences |
| Legal | policy documents, versions, acceptance log |
| Support | tickets, knowledge base, saved replies, assistant |
| Content / Messaging / Themes | page builder + FAQ, WhatsApp bot, storefront themes |

Cross-cutting building blocks (`src/BuildingBlocks`): domain base types + audit stamping (`AuditInterceptor`),
Result/Error types, MediatR pipeline (validation, transactions), the background job abstractions, encryption
(`ICodeProtector`), platform-settings provider.

## Request path

`nginx` → `/api/*` and `/uploads/*`, `/sitemap.xml`, `/robots.txt`, `/health` → Kestrel (`127.0.0.1:5000`) →
minimal-API endpoint → MediatR command/query handler → module `DbContext`. Everything else is the SPA
(`try_files … /index.html`). Rate limiting is per IP (fixed window) on checkout initiation, payment callbacks and
the public support-contact click.

## Order, payment, delivery

1. Checkout creates an **Order** (Pending) and reserves stock (`OrderStockHoldService`, transactional, expiring).
2. A hosted gateway (DOT, DOT-Fawry, Cryptomus, OxaPay) takes payment. **Callbacks only confirm payment** (claim-guarded
   `Pending → Verifying`) and enqueue `ExecuteOrderFulfillment`; they never deliver inline.
3. A 5-minute reconcile sweep per gateway repairs missed callbacks.
4. The **job engine** (`OperationalJobs`, SQL-backed, worker inside the API process) runs fulfillment: local
   inventory first, then the supplier chain. Retries follow the configured schedule (default 0/2/5/15 min + jitter);
   a supplier 429 / `Retry-After` pauses that supplier (`SupplierRateLimitHandler`).
5. Delivered codes are encrypted at rest; customers see them only in the signed-in library, behind an e-mailed OTP
   when the store requires it. E-mail never carries a code, only a link to the library.
6. Orders can be **held** (manual review, admin hold). Every manual action requires a reason and writes an
   `OrderAuditEntry` (actor, reason, old/new value, IP, user-agent).

## Operations and monitoring

- `OperationalAlert` rows are generated by a recurring job (stuck jobs, failed deliveries, low stock, worker
  heartbeat). New critical alerts are e-mailed (`Monitoring:AlertEmails`).
- `GET /api/v1/system/worker-health` (token header) is the external watchdog target; `scripts/worker-watchdog.sh`
  polls it from cron.
- `Admin → Operations → Activity log` is the single searchable log over the order, referral, membership, promotion
  and operations audit trails (CSV export; per-order export on the order page).

## Storefront SEO and analytics

`SeoService` (Angular) sets title/description/Open Graph/canonical/robots and JSON-LD (Organization, WebSite,
Product, BreadcrumbList) from the **SEO** platform settings; the API serves `/robots.txt` and `/sitemap.xml`.
GA4 / GTM / Meta Pixel load **only after the visitor accepts** the cookie notice, and `purchase` is sent once per
order. The storefront is a client-rendered SPA — there is no server-side prerendering.

## Configuration

Secrets and environment values live in `/opt/hambox/.env` and `/opt/hambox/appsettings.Production.json` on the
server (never in git). Everything an operator should change at runtime is a **platform setting** (Admin →
Settings): currency, retry policies and supplier throttling, purchase risk limits, SEO, analytics, e-mail…

## Deployment

`/opt/hambox/scripts/deploy.sh` (run over SSH): `git reset --hard origin/main` for both repos, builds the Angular
bundle in a `node` container, builds the API image, recreates `hambox-api`, waits for `/health`. Database schema is
applied **by hand before** deploying code that needs it: `scripts/deploy-apply-*.sql` (idempotent) after
`/opt/hambox/scripts/backup-db.sh`.
